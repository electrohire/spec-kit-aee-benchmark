## Amendment 2026-10-20: Spec 006 lane outcomes, recorded acts, shared setup and tripwire records

This amendment is prospective only. Frozen episodes, frozen inputs, retained reports and every recorded result under earlier protocol versions are not modified, re-scored or re-admitted under it. It records the harness claims first; the code that carries them follows in the same change.

* PC-1 (recorded acts after each phase assessment). After each AEE phase assessment, the harness records acts on the assessed claim bundle through the engine's recorded-act commands (`aee stage` and `aee ratify`, engine 1.6.0, methodology 2.1), with the pipeline identity `benchmark-pipeline` as the recording actor. A claim qualifies only when at least one of its declared falsification tests was actually executed in that phase, where executed means a tool artifact of the same attempt records a command that matches one of the claim's declared falsification tests, or is cited by the claim's evidence, verifies against the store, and records a test-runner command (a citation to a non-test artifact, such as the specification the phase read, never qualifies a claim). Each qualifying claim receives a `checked` stage event whose basis is a test verdict naming the executed tests and the run artifacts. A qualifying claim still at draft status is ratified out of draft on the same test-verdict basis when every executed check for it passed. Acceptance (stage `accepted`) is recorded only on a test verdict, only when an executed and passing run is the claim's own declared acceptance test, and never on a human basis: the harness records no human act and never records `explained`, which requires a named human's exposition. Before the assessment runs, the phase's real verification artifacts (test-run logs and outputs) are attached to the claims they verify as distinct evidence sources, one item per artifact, so the engine's independence component counts distinct real sources instead of one shared source. A failed or refused act is recorded as such in the assessment record; it does not rewrite the phase result.
* PC-2 (gate eligibility follows lane 1; both lanes are reported). The AEE result carries the engine's two lanes separately: lane 1 is machine verification, lane 2 is human acceptance state. Gate eligibility in the phase workflows — whether a phase proceeds, enters bounded recovery, or blocks the attempt — reads the lane 1 outcome, not the blended headline outcome, falling back to the headline when no lane record exists. The headline outcome is still recorded unchanged, and benchmark records and reports state both lanes explicitly (the lane 1 outcome and the lane 2 stage state) alongside it, so a machine pass with human acceptance still open is visible as exactly that, never as a settled pass.
* PC-3 (campaign setup is frozen once and reused, behind a flag). A campaign manifest may set `share_campaign_setup`. When it does, the constitution/setup phase for a task is executed by the first attempt that needs it, its completion record is frozen into the run store once per campaign and task, and later attempts for the same task in either Spec Kit arm reuse that record instead of issuing new setup calls. A reusing attempt records the reuse, names the source attempt and issues zero setup calls; its own sandbox files are still staged locally as before. The flag defaults to off, so campaigns that do not set it run exactly as before. Reuse carries the recorded setup outcome only: no human acceptance, independence or stage promotion is transferred by it.
* PC-4 (halts are classified and recorded; stop behavior is unchanged). Every attempt that ends other than completed is also recorded as a tripwire event that classifies the halt under the shared taxonomy as one of model outcome, premise or equipment fault, integrity fault, or unknown, with the specific kind named (for example a disclosed limit reached, an operator interrupt, an image or freeze identity mismatch, or an unclassified error). The classification is a record only. It does not change when the workflow stops, what it stops, or any status a run already reports; whether a known model outcome may end only its own trajectory is the owner's pending stop-policy decision and is not pre-empted by this amendment. (Ruled in PC-7; behavior implemented in PC-8, amendment 2026-10-21 below.)
* PC-5 (engine pin and release order). The harness engine requirement is `applied-epistemic-engineering>=1.6.0,<2`, and the recorded pin floor in `manifests/versions.json` is engine 1.6.0 (Spec 006 branch commit `81414c3c8777058ee20bc90ce887be0efa3738a7`, pull request 63 of the engine repository). Release order: engine 1.6.0 is published first; only then is this pin satisfiable from the public package index, and only then can the lockfile be refreshed and public continuous integration resolve dependencies. Until the release, the pin is satisfiable only from the Spec 006 branch, and a public CI failure at dependency resolution is attributable to the pin alone when the logs show exactly that. Local verification for this amendment installed the engine from that branch.
* PC-6 (the frozen upstream coding campaign keeps its own baseline). The stopped upstream coding campaign's admission guard still names engine 1.5.3 exactly, because that campaign's freeze names 1.5.3. It is not re-admissible under the new harness pin and is not re-run; the new pin governs prospective campaigns only.
* PC-7 (the stop policy is ruled; this amendment stays recording-only). On 2026-10-20 the owner adopted the benchmark stop policy as Option B with a nil-review checkpoint (decision paper `2026-10-20-benchmark-stop-policy-decision.md`, RULING section): a failure proven to be the model's own ends only that run and is scored as its result; equipment faults, integrity problems, and anything unexplained still stop the whole study; at a study plan's pre-named nil checkpoint, an *earned* nil (the instrument demonstrably worked and the effect is not there) is the finding and the study closes, while a *manufactured* nil (nothing was ever eligible to succeed) halts like an integrity fault. This pull request does not implement the policy: PC-4's classification stays recording-only and stop behavior is unchanged here. The behavior change lands as a separate prospective protocol revision applying to new studies under new plans only; the four stopped episodes of the upstream coding campaign stay stopped and unchanged, per PC-6. (That revision is PC-8, amendment 2026-10-21 below.)

## Amendment 2026-10-21: the stop policy as behavior (PC-8)

This amendment is prospective only. It implements the owner's 2026-10-20 stop-policy ruling recorded in PC-7, as the separate prospective revision PC-7 promised. It applies to new studies under new plans only; the four stopped episodes of the upstream coding campaign stay stopped and unchanged, per PC-6, and no frozen episode, frozen input, retained report or recorded result under earlier protocol versions is modified, re-scored or re-admitted under it. PC-4's classification semantics are unchanged: every recorded halt, including halts recorded before this amendment, classifies identically.

* PC-8 (behavior follows classification for attempts that started). After a started attempt ends other than completed and its tripwire event is recorded, the schedule's behavior is the classification's behavior. A halt classified `model_outcome` ends only its own attempt: the attempt stands as scored, with its patch, assessment and charges retained, and the schedule continues to the next entry (tripwire `behavior: score_and_continue`). A halt classified `premise_equipment`, `integrity` or `unknown` halts the study: no later attempt starts (tripwire `behavior: halt_study`). An operator interrupt classifies as `premise_equipment` and halts. Classification, not status, decides: a limit halt for the campaign budget classifies as `premise_equipment` and halts, while a limit halt for a disclosed per-attempt limit classifies as `model_outcome` and continues. Tripwire records written under this amendment name the behavior taken in a `behavior` field and carry `behavior_changed: true`; records written before it carry no `behavior` field and `behavior_changed: false`, and are not rewritten.
* Proven model outcomes, and why the proof holds. No new `model_outcome` kinds are created. The only proven model outcomes remain the two PC-4 already maps there: the AEE gate's recovery bound exhausted, and a disclosed limit reached (wall time, call count, attempt token reservation). Both are generated by the harness's own gate and accounting from the attempt's calls ledger, not inferred from the model's prose or from an error message: the gate's recovery count and the accounting's reservation arithmetic are computed over physical calls the ledger records as having been issued and answered, which is the mechanical proof that the model's requests reached the model intact and that the failure is the measured result of the model's own work under disclosed bounds. Anything whose cause is not established in that way stays `unknown` and halts; an error is never promoted into a model outcome because it looks like the model's fault.
* The resume rule. An attempt found in `started` state when a run resumes is recorded as an infrastructure failure, as before, and its class is `unknown` (interrupted attempt, cause never established). Under this amendment the study halts after recording it; the schedule does not proceed to later entries.
* The pre-skip exclusion. The pre-start diagnostic pre-skip for repair-dependent arms is an admission decision made before any attempt starts, not a halt, and this amendment does not govern it: its behavior is unchanged, the schedule continues past a pre-skip, and its tripwire record carries `behavior: skip_and_continue` with `behavior_changed: false`. Downstream band selection still fails closed on the skipped attempts, as before.
